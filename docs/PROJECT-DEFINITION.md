# DevOrchestra 제품 정의

## 제품 완성 우선 원칙

1. 사용자가 실제로 이용할 수 있는 기능을 우선 구현한다.
2. 각 단계에 구체적인 사용자 경험이나 실제 실행 성공 조건을 둔다.
3. 구현 여부, 합성 통과, 실사용 통과, 차단 상태를 각각 `IMPLEMENTED`, `SYNTHETIC_PASS`, `LIVE_PASS`, `BLOCKED`로 구분한다.
4. 새로운 문제나 변경 근거가 있을 때만 이전 검증을 다시 수행한다.
5. 불확실한 권한은 차단하고, 필수 안전 위험과 후속 개선이 가능한 품질 문제를 구분한다.
6. 실제 실행이 막히면 지원되는 대안이나 독립적으로 완성할 다음 사용자 기능을 진행한다.
7. 새로운 보안 요구에는 방지할 구체적 위험과 사용자 기능에 미치는 영향을 명시한다.
8. 검증의 범위는 실제 작동하는 자동 개발 프로그램의 완성에 필요한 만큼으로 정한다.

개발 주기는 구체적인 사용자 기능, 재현 가능한 결함 또는 기능을 직접 가능하게 하는 변경에 귀속한다. 명시적으로 요청받은 문서·보안·성능·테스트는 자체 완료 조건을 가질 수 있다. 신규 검증은 변경 범위와 위험에 비례해 선택하며 반복 통과는 구현 진척으로 집계하지 않는다. 실제 산출물과 검증 영수증을 기준으로 요구사항의 `NOT_STARTED`, `IMPLEMENTED`, `VERIFIED`, `USER_TEST_READY`, `BLOCKED`를 구분한다. 사용자 테스트 준비에는 필요한 실제 빌드·실행·검증 증거가 필요하다.

반복 실패 시 다른 접근이나 사용자 질문으로 전환한다. 필요한 안전 검사는 유지하며, 독립적으로 진행할 수 있는 기능을 우선한다. Reviewer는 실제 요구사항 영향, 결함, 복잡성 및 중복 검증의 근거를 보고하고 취향 차이는 재작업 사유로 삼지 않는다. Verifier는 직접 검사와 영향 범위 회귀를 선택하며 전체 검사는 사용자 요청, 변경 위험 또는 릴리스 인수 조건에 따른다.

기존 ChatGPT/Codex 구독 인증을 사용한다. 별도 과금되는 Responses API, API 키 입력, 과금 계정 전환, 유료 모델 자동 폴백은 금지한다. 승인된 작업은 순차 자동 진행하며 중요한 질문과 권한 변경만 Command Center에서 사용자에게 확인한다.

일반 모드는 공식 Codex 샌드박스와 승인 시스템을 우선한다. VM은 선택적 강화 격리다. 컴퓨터 사용, 화면 캡처, 전역 입력, 타 프로그램의 창·프로세스·메모리 접근, 주입·후킹·디버거 연결, 종료·우선순위 변경, 관리자·시스템 변경 및 미승인 파일·계정 접근을 금지한다. 지침 준수와 OS 집행은 별도로 판정한다.

## 최종 사용자 흐름

배포본의 첫 실행은 저장소 준비와 프로젝트 등록을 분리한다. 초보 사용자는 폴더와 목표를 폼으로 입력하며 개발용 작업 폴더는 원본과 분리한다. 공개 기본 지침을 감독형 작업에 포함하며 개인 전역 지침과 로컬 역할 초안은 사용자가 선택·검토·승인한 뒤 연결한다.

P2.65의 감독형 Codex 모드는 사용자가 기존 구독 Codex에 Manager 지시를 직접 전달하고 JSON 봉투를 가져오는 중간 단계다. Controller가 현재 작업·기준본·범위·출력 계약을 확인한 뒤 질문 또는 Developer 인계 초안을 제공한다. 파일 변경과 실행 승인은 별도이며, 실제 역할 자동 실행은 최종 제품 목표로 유지한다.

프로젝트 폴더 지정 → 요구사항 등록 → 자동 개발 시작 승인 → 결과 확인 → 사용자 직접 테스트 → 개선 문서 등록 → 후속 개발을 반복한다. 여러 프로젝트를 등록할 수 있으며 실제 활성 프로젝트·작업·에이전트·실행 슬롯은 전역에서 각각 하나다. Controller가 계획·구현·검토·결정적 검증·최종 결정을 조율한다.

요구사항은 목표·기능·설계·버그·개선으로 분류하고 원본 폴더 기준 상대경로, 버전, 해시, 등록 시점과 관련·대체 문서를 추적한다. 각 개발 세션은 시작 때 요구사항 버전을 고정한다. 후속 세션은 새로 등록된 버전을 읽고 이전 검증 증거와 영향 관계를 대조해야 한다. 원본은 보존하고 실제 개발은 승인 복제본에서 수행한다. 모순 또는 승인 범위 변경은 필요한 부분만 확인한다.

이번 주기의 요구사항 충족과 전체 목표 완료를 구분한다. 실제 필수 증거를 확인한 주기만 사용자 테스트 대기로 표시하고 변경 목록, 검증 및 미검증 결과, 남은 위험, 테스트 가능한 버전·실행 방법과 Git 상태를 제공한다. Command Center의 기본 화면에는 프로젝트·요구사항·진행·결과를 두고, 역할 설정·예산·지침·승인·복구는 고급 항목으로 제공한다.

기본 실행 후보는 Windows Native Codex다. VirtualBox·게스트 이미지 없이 초기 설정할 수 있다. 승인 복제본과 소유 자식의 OS 격리가 입증되기 전에는 실제 자동 개발을 차단한다.

## 예산 보류와 장애 복구

사용자가 고정 토큰 수와 비율로 예비량을 설정한다. Trusted Controller는 확인된 사용량과 다음 역할의 최대 사용량을 대조하고 부족하면 새 역할 대신 종료를 예약한다. 계정 할당량과 로컬 예산은 별개다. 복구는 검증된 원장·체크포인트와 명시적 사용자 요청으로 진행하며 미확정 외부 작업은 자동 반복하지 않는다.

## 종료 예약과 다른 PC의 초기 설정

종료 예약은 현재 역할의 안전 경계에서 새 입장을 닫고, 완료 증거와 미완료 상태를 원장에 남긴다. 재시작은 동일 복제본·Git 기준·승인·예산·권한·소유 자원 회수 증거를 요구한다. 작업 결과가 불명확하면 자동 재실행이나 완료 처리를 차단한다.

Windows x64 초기 설정은 원본, 복제본, 로컬 상태와 자격증명 경계를 구분한다. 설정 완료는 실행 허가를 부여하지 않는다. 사용자가 다른 앱을 이용하는 동안의 비간섭은 생성 코드·빌드·테스트에도 필수이며, OS 실측과 소유 프로세스 회수 검증을 별도로 통과해야 한다.

## 최우선 인수 조건

사용자가 게임과 다른 앱을 평소처럼 이용하는 동안 DevOrchestra는 승인된 프로젝트 복제본에서 독립적으로 자동 개발한다. 사용자 앱의 존재를 감지하거나 관찰하거나 조작하지 않는다. 생성한 코드와 빌드·테스트도 같은 경계를 지킨다. 프로젝트 자체가 외부 프로세스 접근, 전역 입력, 화면 캡처 또는 다른 창 제어를 요구하면 작업을 차단하고 이유를 사용자에게 표시한다.

완성 흐름은 프로젝트 선택 → 권한·예산 확인 → Manager → Developer → Reviewer → Verifier → 증거를 검토하는 Manager → 승인 범위 내 Controller 커밋이다. 사용자 취소, 소유 자원 회수, 상세 감사 및 별도 Git 권한이 전 과정에 적용된다.

P2.4는 역할 이벤트를 하나씩 영속 저장하고 확인된 기록과 미확인 수신을 구분한다. 제공자 완료, 자원 회수, 실제 검증 및 사용량 정산은 별도 증거다. 현재 수집·정산 경로는 합성 입력에 한정된다.

P2.3 개발 세션은 한 프로젝트의 동결된 목표·설정 아래 작업 주기를 직렬로 연결한다. 세션 전체 예산과 작업별 승인을 적용하며, 관리자 제안은 Trusted Controller가 검증한 후 반영한다. 현재 CLI가 세션을 진행하고 Command Center는 원장 증거를 조회한다.

Windows 로컬 개발 관리 앱이다. 사용자는 프로젝트별 목표·지침·모델·추론·권한·시간·토큰·비용을 정하고, 관리자 → 개발자 → 검토자 → 결정적 검증기 → 관리자 판정을 순서대로 실행한다. 승인, 중단, 결과 확인은 사용자가 통제한다.

P2.2는 단일 사용자 프로필의 등록부에 프로젝트 목표·완료 조건·경로 참조·역할 설정·예산·요청 권한·Git 정책·마지막 인수인계를 저장한다. 실행 원장과 등록부를 분리하고, 등록된 프로젝트도 승인 후 합성 작업만 수행한다. 실제 프로젝트 파일 접근, 사용자 인증과 OS 격리는 후속 단계다.

## 시각 콘솔

프로젝트 카드, 단계 진행 표시, 역할 패널, 예산 수치, 이벤트 패널은 검증된 원장에서 읽는다. 단계 진행은 완료 이벤트에 근거하며 임의의 퍼센트나 추정 활성 상태를 표시하지 않는다. 실제 시스템 상태는 결정적 상태 전이, 모델 설명은 별도로 표시할 비신뢰 제안, 색·아이콘은 장식, 근거 데이터는 감사 이벤트·테스트·Git·승인·계측 레코드다. Mock 결과와 합성 토큰에는 명시적으로 출처를 표시한다.

P1 인수 기준은 [아키텍처](ARCHITECTURE-ROADMAP.md)와 [현재 상태](CURRENT-STATUS.md)에 기록한다.
