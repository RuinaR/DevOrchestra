# DevOrchestra 제품 정의

사용자는 최종 목표, 완료 기준, 복제본, 허용 작업과 전체 예산을 한 번 승인한다. Controller는 한 번에 하나의 역할을 실행하고 Manager 계획, Developer, 독립 Reviewer, 결정적 Verifier, 최종 Manager를 순서대로 연결한다. 최종 Manager가 검증된 작업 이후 남은 목표를 제시하면 남은 시간과 토큰 예산 안에서 다시 계획한다. 사용자는 사이클 상한을 선택할 수 있다. 먼저 도달한 시간·토큰·사이클 한도, 권한 부족, 철회, 무진척, 미확정 응답은 새 역할의 시작을 막는다.

제품 실행 모드는 일반 개발 하나다. 공식 Codex가 인증·모델 통신을 처리한다. Controller는 승인된 독립 Git 복제본, 역할별 도구 권한, 단일 슬롯, Job 회수, 예산과 독립 검증을 집행한다. 기존 환경의 실제 두 사이클, 등록 텍스트 프로젝트의 재개, 2D 게임 파일럿의 Windows 실행을 관측했다. 신규 사용자 환경의 로그인과 실제 자동 개발은 릴리스 후보 검증 범위다. 실제 원본 반영, 외부 계정 변경, 결제와 실서비스 배포는 별도 승인을 사용한다.

프로젝트의 빌드 구성과 의존성 파일을 작업 계획에 반영한다. 모델이 제안한 빌드·실행·테스트는 승인 범위에서 수행하며, 독립 Verifier는 사용자가 연결한 검사와 증거만 판정한다. 산출물 변경, 문서 마일스톤, 실제 기준의 검증 진척을 구분한다. Windows GUI 검토는 소유 스테이징에서 선언한 실행 파일과 해시가 일치하는 번들을 대상으로 한다.

반복되는 문제는 공통 실행·검증 계약에서 해결한다. 프로젝트별 경로, 실행 파일명, 엔진 버전은 승인된 설정과 검증 어댑터에서 해석한다. 공통 변경은 영향을 받는 여러 프로젝트 유형에서 확인한다. Reviewer는 재현 가능한 문제와 후속 검사 방법을 Developer에게 전달한다.

Command Center는 최근 승인 세션의 동결 기준 중 독립 확인된 비율을 표시한다. 구현 검토, 재작업, 검증 실패, 입력 대기와 미검증은 별도로 표시한다. 프로젝트별 개발 설정은 사용자 저장소에 보관하고, 세션 시작이나 재개 시 Controller가 실제 승인 계약을 다시 확인한다.

검증된 공개 릴리스 ZIP은 승인 원장과 연결해 로컬에 보존한다. 세션마다 정확한 버전과 해시를 대조하고 실행용 사본만 작업 영역에 풀어 쓴다. 네트워크 준비 실패 시 확인된 도구나 독립 작업을 우선 검토한다.

새 등록 프로젝트 세션은 토큰 한도 또는 **구독 잔여량 기반 개발** 중 선택할 수 있다. 구독 모드는 DevOrchestra의 토큰 상한 없이 공급자의 포함 사용 허용 여부와 공식 잔여량을 확인한다. 가장 낮은 잔여량이 10% 이하이면 현재 작업을 보존하고 새 개발을 시작하지 않는다. 시간·안전 제한과 검토·독립 검증 계약은 계속 적용한다. 유료 크레딧 사용 가능성이 보고되면 호출을 보류하며 결제·초기화 기능을 제공하지 않는다.

소규모 게임은 다음 실사용 실증 대상이다. Manager는 사용자 목표와 동결 완료 기준을 유지하면서 게임 기획과 검증 시나리오를 제안한다. 완료 판정은 실제 Windows 내보내기와 플레이 가능한 흐름, 소유 창의 입력과 화면 관측, 라이선스 기록을 요구한다. 엔진 시작이나 에셋 가져오기만으로 게임 완료를 판정하지 않는다.

DevOrchestra는 코딩 에이전트의 실행 순서, 권한, 예산, 감사와 복구를 관리한다. 실제 코딩은 공식 Codex 실행기를 재사용하는 것이 목표다. SDK를 우선 검증하고 App Server와 CLI, 공식 구독 텍스트 호출을 별도 후보로 관리한다. 자동 실행 기본값은 실측을 통과한 후 결정한다.

구독 텍스트 Manager는 별도 OAuth 동의와 승인된 요구사항만 사용한다. Developer·Reviewer의 SDK 실행과 결정적 Verifier는 별도 권한 경계를 유지한다.

승인된 구독 텍스트 Developer 변경은 같은 작업의 읽기 전용 Reviewer, 결정적 Verifier, 최종 Manager로 인계할 수 있다. 완료에는 모델 판단과 해시가 연결된 실제 Verifier PASS가 필요하다. 한 파일의 고정 Python 벡터 세션은 전체를 한 번 승인해 제한된 자동 재작업까지 수행할 수 있다. 개별 역할 승인 경로도 유지한다.

등록된 데이터 전용 WinForms 시험은 승인된 상태 문구 한 필드와 동결한 GUI 시나리오에 한해 같은 세션에서 실행할 수 있다. 그 변경에서 빌드한 소유 EXE의 관측 영수증을 최종 판정에 요구한다.

승인된 루트 Python 파일 2~4개를 한 배치로 수정할 수 있다. 새 파일은 사전에 지정한다. 파일별 구문 검사와 고정 벡터는 임의 Python 실행과 별도다. 데이터 전용 GUI의 실제 관측 실패는 동결 테스트를 유지한 채 자동 재작업에 전달한다.

고정 Python 매니페스트를 승인한 다중 파일 세션은 읽기 전용 입력 복사본을 MXC에서 실제 컴파일하고, 검토된 함수 문법에 한해 CPython의 출력과 종료 코드를 확인한다. 프로젝트 스크립트·임의 빌드 명령·생성 EXE는 별도 실행 계약이 필요하다.

다중 모듈 매니페스트에는 진입 모듈과 로컬 import 관계를 명시한다. Verifier는 승인된 바이트코드에서 실제 import와 파일 간 함수 호출을 관측하고, 실패 입력·기대값·관측값·종료 코드와 영수증 해시를 같은 세션의 재작업에 전달한다. 표준 라이브러리 import, 순환·동적 import, 패키지 초기화 코드와 플러그인은 이 경로에서 차단한다.

공통 빌드 Verifier는 등록 복제본과 도구별 실행 범위를 검토 해시에 묶는다. 첫 .NET 어댑터는 검토된 두 C# 소스를 MXC에서 Roslyn으로 직접 컴파일하고 콘솔 DLL을 검증한다. 일반 MSBuild 프로젝트와 모델 변경 C#은 별도 실행 검증이 필요하다.

개발 도구는 프로젝트 요구사항과 호환되는 설치를 탐색하고 세션 승인에 버전과 신원을 고정한다. 현재는 등록 복제본의 개발 환경 표식과 설치된 .NET 도구를 조사한다. 프로젝트 전용 자동 설치는 출처·무결성·네트워크와 설치 부작용에 대한 승인 및 검증이 갖춰져야 한다.

프로젝트 전용 .NET SDK의 정확 버전은 별도 승인으로 설치할 수 있다. 구독 C# 자동 개발은 두 산술 모듈을 바꾸는 검증된 계약부터 지원한다.

완전자동 개발은 단일 슬롯에서 계획, 구현, 독립 검토, 결정적 검증, 최종 판정을 순차 실행하는 것을 목표로 한다. 개발 세션에 테스트 앱과 도구 범위를 묶어 승인하고 범위 안에서 반복 QA한다. UI가 바뀌면 실제 렌더링과 동작을 확인하고 소유 자원 회수를 기록한다. 금융 거래, 외부 계정 변경과 운영 배포에는 각각 별도 승인이 필요하다.

## 시간에 민감한 GUI·실시간 QA

게임, 데스크톱 앱, 서버에서 AI가 화면을 읽고 판단하는 동안 대상 상태가 변하면 검증 목적에 맞는 시간 모델을 계획한다. 정상 속도는 실제 조작감, 반응성, 애니메이션, 프레임 성능, 네트워크 지연과 실제 시계를 검사할 때 사용한다. 대상이 제공하는 감속은 빠른 상태 전이를 관찰하는 데 쓴다. 논리적 시간이 중요한 기능은 정지·단계 실행이나 가상 시계, 결정적 이벤트를 우선 검토한다.

단계 실행을 지원하는 QA 대상에서는 관련 시뮬레이션을 정지한 뒤 화면과 상태를 관찰한다. AI의 판단이 끝날 때까지 상태를 유지하고, 승인된 입력 묶음을 적용한 뒤 지정한 논리 시간 또는 틱만 진행한다. 다시 정지해 결과를 확인한다. 재현 가능한 초기 상태를 사용하고 필요하면 난수 시드를 고정한다. WPF·WinForms·서버·비동기 앱에서 화면 조작보다 직접적인 방법이 있다면 주입 가능한 시계, 결정적 스케줄러, 수동 이벤트, 모의 지연 또는 비동기 완료 제어를 선택한다.

- **Unity**에서는 프로젝트가 실제 사용하는 엔진 버전의 `Time.timeScale`, `Time.deltaTime`, `Time.unscaledDeltaTime`, `FixedUpdate`와 물리 간격을 확인한다. 배율을 0으로 설정하면 `FixedUpdate`와 `WaitForSeconds` 대기가 멈추므로, 실제 코루틴의 대기 유형과 Animator의 업데이트 모드도 확인한다. QA 틱이 필요하면 별도의 진행 계약을 검증한다. [Unity Time.timeScale](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/time/timescale) · [Unity Time.unscaledDeltaTime](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Time-unscaledDeltaTime.html) · [Unity AnimatorUpdateMode](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AnimatorUpdateMode.html)
- **Godot**에서는 `SceneTree.paused`와 노드의 `ProcessMode`, 물리 서버 상태, `Engine.time_scale`을 확인한다. `Always`나 `WhenPaused` 노드와 신호 처리, Timer·SceneTreeTimer·Tween의 정지·실시간 설정을 실제 코드와 대조한다. 시간 배율 변경과 결정적 단계 실행은 각각 필요한 증거를 확보한다. [Godot Pausing games and process mode](https://docs.godotengine.org/en/stable/tutorials/scripting/pausing_games.html) · [Godot Engine](https://docs.godotengine.org/en/stable/classes/class_engine.html) · [Godot Timer](https://docs.godotengine.org/en/stable/classes/class_timer.html) · [Godot SceneTree](https://docs.godotengine.org/en/stable/classes/class_scenetree.html) · [Godot Tween](https://docs.godotengine.org/en/stable/classes/class_tween.html)

사용자 반응성, 실제 애니메이션 속도, 게임 난이도와 밸런스, FPS·프레임 시간, 물리 안정성, 실제 타이머, 비동기 경쟁 상태, 장시간 안정성과 사용자 플레이 흐름은 해당 기준에 필요할 때 정상 속도에서 별도로 확인한다. QA 보고에는 적용 시간 모델, 실제·논리 경과나 틱 수, 배율, 입력·관찰 구간, 제어 출처, 관측 결과 및 남은 정상 속도 검증 중 필요한 항목을 기록한다.

시간 제어는 승인된 복제본이나 소유 시험 실행 파일에서 대상이 제공하는 제어 또는 승인된 QA 코드로 한정한다. 정상 배포 동작을 보존하고 시험 종료 시 입력·시간 설정을 복원한다. 기존 Controller의 실제 시간 한도, 중단·회수 계약과 완료 기준은 계속 적용한다. 현재 변경은 QA 작업 지침과 프롬프트에 적용되며 각 프로젝트의 일시정지나 단계 실행은 그 프로젝트에서 지원 여부와 실제 증거를 별도로 확인한다.

등록 개발의 최초 세션 승인에서 Codex 인터넷 자료 조사와 프로젝트 전용 포터블 도구 설치를 선택할 수 있다. 계획 Manager와 Developer는 승인된 공식 Codex 검색으로 공개 자료를 조사하고 출처를 남긴다. 계획 Manager가 개발 중 필요한 공개 GitHub 릴리스 ZIP 또는 커밋 고정 소스 ZIP을 선택하면 Controller가 출처와 무결성을 확인하고 복제본에서 제공한다. 같은 세션에서는 조사·설치마다 추가 승인이 필요 없다. 명령 네트워크와 시스템 전체 설치는 꺼져 있다.

## 제품 완성 우선 원칙

### 실제 기존 프로젝트의 인수 기준

기존 Git 온보딩은 등록, 문맥 검토, 복제본 준비 상태를 구분한다. 원본의 커밋과 변경 분류를 로컬 원장에 고정하고 승인된 작업 파일로 독립 Git 기준을 만든다. 빌드·환경 검증과 개발 승인 또는 원본 반영은 별도 기능이다.

등록 프로젝트의 Codex 세션은 온보딩 복제본, 목표, 완료 기준, 변경 파일, 설치된 검증 도구와 사용량을 최초 승인에 묶는다. Verifier는 기준별로 소유자가 승인한 설치 EXE와 인자를 읽기 전용 MXC에서 실행한다. 기대 출력과 종료 상태를 독립적으로 확인하고, 세션 결과와 원본 반영 승인을 분리한다.

사용자가 AI 시각 검토를 승인하면 개발을 먼저 시작할 수 있다. Controller는 Developer가 준비한 Windows 미리보기의 시작 화면을 캡처하거나, 설정된 검증 도구로 소유 창의 입력 전후 화면을 수집한다. 화면이 없으면 코드 검토를 진행하고 시각 검토를 미확인으로 기록한다. 읽기 전용 Reviewer는 기존 Codex CLI 호출에 첨부된 PNG 최대 네 장에서 관찰과 결함을 기록한다. 재현 가능한 결함은 다음 계획과 Developer 수정에 전달한다. 결정적 Verifier는 실행 결과와 캡처 무결성을 확인한다. 최종 Manager는 시각 의견과 독립 검증 결과를 각각 근거로 사용한다.

AI 플레이를 승인하면 Reviewer가 소유 게임 창의 이미지를 보고 다음 행동을 제안한다. Controller는 제한된 키 입력·클릭·이동·대기만 집행하고 결과 화면을 기록한다. 사전 설정된 검증 입력, 모델 제안, 실제 창 메시지와 결과를 구별한다. 화면 해시가 바뀌었다는 사실만으로 게임 기능을 검증하지 않는다. Windows 공식 데스크톱 Computer Use는 활성 데스크톱을 제어하므로 현재 자동 세션의 소유 창 전용 입력으로 연결할 수 없다. [Windows Computer Use](https://learn.chatgpt.com/docs/computer-use#windows-foreground-use)

최종 제품은 복원된 AITrader, AVManager, LumiPeek, MarketCrate 같은 기존 프로젝트를 한 Command Center에 등록해 순차 개발하는 데 사용한다. 현재 네 프로젝트의 준비 상태는 모두 **NOT_VALIDATED**다. EchoMate는 개발 중단으로 활성 후보에서 제외하며 과거 이력은 보존한다. P2.102의 두 C# 산술 파일 실측은 지원하는 한 경로의 증거다.

1. 승인된 범위의 프로젝트 AGENTS.md, 개인 지침, 인수인계 및 Git 상태를 읽고 작업 문맥을 복구한다. 개인 지침과 인증자료는 로컬에 보존한다.
2. 언어·엔진·SDK·컴파일러·잠금 파일과 종속성을 탐색한다. 호환 도구를 재사용하거나 승인된 공급 경로로 프로젝트 전용 설치한다.
3. 소스와 Git 이력, 미커밋·미추적 파일, DB·모델·인증자료·로컬 설정을 보호한다. 변경은 승인된 복제본에서만 시작하고 검증과 원본 기준 재확인을 통과한 변경만 반영한다.
4. 한 번의 개발 승인으로 Manager → Developer → Reviewer → Verifier → Manager와 승인 범위 내 재작업이 순차 진행된다. 모델·빌드·검증을 포함해 활성 작업은 하나다.
5. 실제 여러 파일·폴더를 변경하고 실제 빌드·테스트·GUI를 검증한다. Windows의 기존 사용자 앱과 비소유 프로세스에는 간섭하지 않는다.
6. 임시 자료는 단계별로 회수한다. 완료 전 최종 산출물, 구버전 빌드, 중복 문서 및 복구 참조를 감사한다.
7. 실거래·결제·외부 계정 변경·공개 배포는 일반 개발 승인과 분리한다. AITrader의 기본 검증은 실주문 전송이 차단된 모의·격리 환경에서 수행한다.
8. 결과에는 코드 변경, 빌드·테스트, 대표 GUI 이미지, 남은 문제, 자원 정리 및 Git 상태를 포함한다.

1. 사용자가 실제로 이용할 수 있는 기능을 우선 구현한다.
2. 각 단계에 구체적인 사용자 경험이나 실제 실행 성공 조건을 둔다.
3. 구현 여부, 합성 통과, 실사용 통과, 차단 상태를 각각 `IMPLEMENTED`, `SYNTHETIC_PASS`, `LIVE_PASS`, `BLOCKED`로 구분한다.
4. 새로운 문제나 변경 근거가 있을 때만 이전 검증을 다시 수행한다.
5. 불확실한 권한은 차단하고, 필수 안전 위험과 후속 개선이 가능한 품질 문제를 구분한다.
6. 실제 실행이 막히면 지원되는 대안이나 독립적으로 완성할 다음 사용자 기능을 진행한다.
7. 새로운 보안 요구에는 방지할 구체적 위험과 사용자 기능에 미치는 영향을 명시한다.
8. 검증의 범위는 실제 작동하는 자동 개발 프로그램의 완성에 필요한 만큼으로 정한다.

개발 주기는 구체적인 사용자 기능, 재현 가능한 결함 또는 기능을 직접 가능하게 하는 변경에 귀속한다. 명시적으로 요청받은 문서·보안·성능·테스트는 자체 완료 조건을 가질 수 있다. 신규 검증은 변경 범위와 위험에 비례해 선택하며 반복 통과는 구현 진척으로 집계하지 않는다. 실제 산출물과 검증 영수증을 기준으로 요구사항의 `NOT_STARTED`, `IMPLEMENTED`, `VERIFIED`, `USER_TEST_READY`, `BLOCKED`를 구분한다. 사용자 테스트 준비에는 필요한 실제 빌드·실행·검증 증거가 필요하다.

반복 실패 시 다른 접근이나 사용자 질문으로 전환한다. 필요한 안전 검사는 유지하며, 독립적으로 진행할 수 있는 기능을 우선한다. Reviewer는 실제 요구사항 영향, 결함, 복잡성 및 중복 검증의 근거를 보고하고 취향 차이는 재작업 사유로 삼지 않는다. Verifier는 직접 검사와 영향 범위 회귀를 선택하며 전체 검사는 사용자 요청, 변경 위험 또는 릴리스 인수 조건에 따른다.

기존 ChatGPT/Codex 구독 인증을 사용한다. 별도 과금되는 Responses API, API 키 입력, 과금 계정 전환, 유료 모델 자동 폴백은 금지한다. 승인된 작업은 순차 자동 진행하며 중요한 질문과 권한 변경만 Command Center에서 사용자에게 확인한다.

공식 Codex 샌드박스와 승인 시스템을 적용한다. VM·WSL·전용 계정·WFP·프록시 실측은 역사 기록으로 보존한다. 일반 개발의 GUI QA는 Controller가 소유권을 확인한 창에서 실행·입력·리사이즈·캡처를 허용한다. 등록 시에는 실행 권한을 부여하지 않는다. 승인된 역할과 대상이 같으면 한 번의 세션 승인으로 정해진 횟수만큼 반복할 수 있다. 전역 입력, 혼합 데스크톱 캡처 및 미승인 앱·파일·계정 접근은 기본 범위에서 제외한다.

## 최종 사용자 흐름

개발 운영실은 프로젝트 전체의 목표와 완료 기준, 이번 차수의 요구사항, 감독형 작업의 다음 행동을 구분한다. 감독형 Codex는 사용자가 지시와 결과를 직접 전달하는 모드다. 일반 모드의 개발 대상은 프로젝트와 승인 작업 폴더로 제한한다. 무관한 사용자 앱의 입력·창·프로세스·메모리·화면 접근과 전역 입력·혼합 데스크톱 캡처·후킹·주입은 금지한다. OS 수준 비간섭은 검증한 경로에 한해 판정한다.

배포본의 첫 실행은 저장소 준비와 프로젝트 등록을 분리한다. 초보 사용자는 폴더와 목표를 폼으로 입력하며 개발용 작업 폴더는 원본과 분리한다. 공개 기본 지침을 감독형 작업에 포함하며 개인 전역 지침과 로컬 역할 초안은 사용자가 선택·검토·승인한 뒤 연결한다.

P2.65의 감독형 Codex 모드는 사용자가 기존 구독 Codex에 Manager 지시를 직접 전달하고 JSON 봉투를 가져오는 중간 단계다. Controller가 현재 작업·기준본·범위·출력 계약을 확인한 뒤 질문 또는 Developer 인계 초안을 제공한다. 파일 변경과 실행 승인은 별도이며, 실제 역할 자동 실행은 최종 제품 목표로 유지한다.

프로젝트 폴더 지정 → 요구사항 등록 → 자동 개발 시작 승인 → 결과 확인 → 사용자 직접 테스트 → 개선 문서 등록 → 후속 개발을 반복한다. 여러 프로젝트를 등록할 수 있으며 실제 활성 프로젝트·작업·에이전트·실행 슬롯은 전역에서 각각 하나다. Controller가 계획·구현·검토·결정적 검증·최종 결정을 조율한다.

요구사항은 목표·기능·설계·버그·개선으로 분류하고 원본 폴더 기준 상대경로, 버전, 해시, 등록 시점과 관련·대체 문서를 추적한다. 각 개발 세션은 시작 때 요구사항 버전을 고정한다. 후속 세션은 새로 등록된 버전을 읽고 이전 검증 증거와 영향 관계를 대조해야 한다. 원본은 보존하고 실제 개발은 승인 복제본에서 수행한다. 모순 또는 승인 범위 변경은 필요한 부분만 확인한다.

이번 주기의 요구사항 충족과 전체 목표 완료를 구분한다. 실제 필수 증거를 확인한 주기만 사용자 테스트 대기로 표시하고 변경 목록, 검증 및 미검증 결과, 남은 위험, 테스트 가능한 버전·실행 방법과 Git 상태를 제공한다. Command Center의 기본 화면에는 프로젝트·요구사항·진행·결과를 두고, 역할 설정·예산·지침·승인·복구는 고급 항목으로 제공한다.

기본 실행 후보는 Windows Native Codex다. VirtualBox·게스트 이미지 없이 초기 설정할 수 있다. 승인 복제본과 소유 자식의 OS 격리가 입증되기 전에는 실제 자동 개발을 차단한다.

## 예산 보류와 장애 복구

사용자가 고정 토큰 수와 비율로 예비량을 설정한다. Trusted Controller는 확인된 사용량과 다음 역할의 최대 사용량을 대조하고 부족하면 새 역할 대신 종료를 예약한다. 계정 할당량과 로컬 예산은 별개다. 복구는 검증된 원장·체크포인트와 명시적 사용자 요청으로 진행하며 미확정 외부 작업은 자동 반복하지 않는다.

## 종료 예약과 다른 PC의 초기 설정

종료 예약은 현재 역할의 안전 경계에서 새 입장을 닫고, 완료 증거와 미완료 상태를 원장에 남긴다. 재시작은 동일 복제본·Git 기준·승인·예산·권한·소유 자원 회수 증거를 요구한다. 작업 결과가 불명확하면 자동 재실행이나 완료 처리를 차단한다.

Windows x64 초기 설정은 원본, 복제본, 로컬 상태와 자격증명 경계를 구분한다. 설정 완료는 실행 허가를 부여하지 않는다. 사용자가 다른 앱을 이용하는 동안의 비간섭은 생성 코드·빌드·테스트에도 필수이며, OS 실측과 소유 프로세스 회수 검증을 별도로 통과해야 한다.

## 최우선 인수 조건

DevOrchestra는 승인된 프로젝트 복제본에서 독립적으로 개발하는 것을 목표로 한다. 사용자 앱을 감지·관찰·조작하지 않으며 생성 코드와 빌드·테스트에도 이 경계를 적용한다. Controller가 소유권을 확인한 창의 입력과 캡처는 승인된 QA에 포함된다. 외부 프로세스 접근, 전역 입력, 범위 없는 화면 캡처와 다른 창 제어는 차단 사유다.

완성 흐름은 프로젝트 선택 → 권한·예산 확인 → Manager → Developer → Reviewer → Verifier → 증거를 검토하는 Manager → 승인 범위 내 Controller 커밋이다. 사용자 취소, 소유 자원 회수, 상세 감사 및 별도 Git 권한이 전 과정에 적용된다.

P2.4는 역할 이벤트를 하나씩 영속 저장하고 확인된 기록과 미확인 수신을 구분한다. 제공자 완료, 자원 회수, 실제 검증 및 사용량 정산은 별도 증거다. 현재 수집·정산 경로는 합성 입력에 한정된다.

P2.3 개발 세션은 한 프로젝트의 동결된 목표·설정 아래 작업 주기를 직렬로 연결한다. 세션 전체 예산과 작업별 승인을 적용하며, 관리자 제안은 Trusted Controller가 검증한 후 반영한다. 현재 CLI가 세션을 진행하고 Command Center는 원장 증거를 조회한다.

Windows 로컬 개발 관리 앱이다. 사용자는 프로젝트별 목표·지침·모델·추론·권한·시간·토큰·비용을 정하고, 관리자 → 개발자 → 검토자 → 결정적 검증기 → 관리자 판정을 순서대로 실행한다. 승인, 중단, 결과 확인은 사용자가 통제한다.

P2.2는 단일 사용자 프로필의 등록부에 프로젝트 목표·완료 조건·경로 참조·역할 설정·예산·요청 권한·Git 정책·마지막 인수인계를 저장한다. 실행 원장과 등록부를 분리하고, 등록된 프로젝트도 승인 후 합성 작업만 수행한다. 실제 프로젝트 파일 접근, 사용자 인증과 OS 격리는 후속 단계다.

## 시각 콘솔

프로젝트 카드, 단계 진행 표시, 역할 패널, 예산 수치, 이벤트 패널은 검증된 원장에서 읽는다. 단계 진행은 완료 이벤트에 근거하며 임의의 퍼센트나 추정 활성 상태를 표시하지 않는다. 실제 시스템 상태는 결정적 상태 전이, 모델 설명은 별도로 표시할 비신뢰 제안, 색·아이콘은 장식, 근거 데이터는 감사 이벤트·테스트·Git·승인·계측 레코드다. Mock 결과와 합성 토큰에는 명시적으로 출처를 표시한다.
