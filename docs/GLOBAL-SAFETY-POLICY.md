# DevOrchestra 전역 안전 정책

P2.34부터 일반 개발과 강화 격리의 인수 조건을 구분한다. 일반 개발은 공식 Codex 샌드박스·승인 정책의 유효성, 승인 복제본·도구 범위, 소유 프로세스, 예산·종료·복구와 실제 검증 영수증을 요구한다. 강화 격리는 추가로 A/B/C 실측을 요구한다. 일반 모드는 무제한 실행으로 대체하지 않으며, 다른 앱 접근 금지와 운영 데이터 보호는 두 모드 모두에 적용한다.

적용 대상은 DevOrchestra의 역할, 등록 프로젝트, 작업 복제본과 외부 도구다. 과거 데스크톱 동시 실행 정책과 프로젝트별 사례는 [이전 정책 이력](https://github.com/RuinaR/DevOrchestra/blob/b049fff4571c3c248a3bab7b88e2243cccc885ec/docs/GLOBAL-SAFETY-POLICY.md)에 보존한다.

P1 런타임은 고정 합성 입력만 실행한다. `approve`는 로컬 소유자 콘솔에서 합성 읽기 요청 한 건을 승인한다. 실제 파일·명령·계정 권한은 부여할 수 없다. 중단된 역할은 UNKNOWN으로 남기며 명시 복구 후 취소한다. 구현과 미검증 경계는 [현재 상태](CURRENT-STATUS.md)를 참조한다.

P2 소유 Job 검증은 개발 테스트의 고정 합성 프로그램과 별도 승인한 진단으로 제한한다. 작업 세대에 귀속된 실행 의도를 먼저 저장하고, Win32 Job에 생성 시 편입된 자식만 다룬다. 소유 트리 활성 수 0과 핸들 정리를 확인한 영수증 없이 다음 실행을 허용하지 않는다. 강제 종료나 기록 실패로 종료 증거가 유실되면 명시 복구 요청도 UNKNOWN을 보존하며 자동 해제하지 않는다.

P2 전체 통과에는 소유 자원 종료 또는 안전한 격리(A), OS의 비인가 파일·네트워크·자격증명 접근 거부(B), 검증 전 게스트의 호스트 저장소·원장 변경 방지(C)가 모두 필요하다. 게스트의 해시나 종료 주장은 승인 또는 종료 증거가 아니다. 검역을 통과한 바이트도 별도 적용 승인과 trusted Runner의 재확인 전에는 공개하거나 적용할 수 없다.

> 최우선 원칙: **하나의 프로젝트, 하나의 작업, 하나의 에이전트, 하나의 실행 슬롯.** 작업 속도보다 사용자 PC·운영 자산·신뢰할 수 있는 결과를 우선한다. 정책을 텍스트로 썼다고 실제 격리가 구현된 것은 아니다. 누락된 강제 제어는 차단 사유다.

## 1. 근거와 적용 범위

- 사용자의 확정 요구: 완전한 순차 실행, 프로젝트별 지침·목표, 에이전트별 상세 작업기록, Windows 개인 PC, 사용자가 선택한 모델·시간·토큰·실행 권한.
- 문서 참고: OpenAI Codex의 AGENTS 지침·샌드박스/승인 원칙, GitHub secret scanning/push protection. 세부 링크는 REFERENCES.md.
- 이 정책은 DevOrchestra에 등록된 **미래의 모든 프로젝트**에 적용할 상한이다. 기존 프로젝트 내부 지침보다 완화되지 않는다. 상충하면 일시정지·사용자 확인. 실제 사용자 승인도 플랫폼 정책/안전 제한을 위반하도록 만들 수 없다.

## 2. 기본 보안 태세 — deny by default

첫 실행/프로젝트 추가/재시작/새 모델/새 작업에서는 항상:
```text
mode=READ_ONLY
dry_run=true
network=OFF
filesystem_write=OFF
project_execution=OFF
gpu_execution=OFF
external_account_login=OFF
production/live_actions=OFF
git_commit=OFF
git_push=OFF
desktop_computer_use=OFF
background_service=OFF
```
소유자가 개발 세션에서 작업 복제본, 역할, 허용 도구·대상, 예산과 만료를 승인하면 명시된 로컬 작업을 범위 안에서 반복할 수 있다. 목표 범위는 코드 수정·빌드·실행·소유 창 QA·오류 수정·재검증이다. 현재 Controller의 반복 승인은 등록 GUI 시나리오에 연결돼 있다. 등록과 연구/분석은 실행 권한을 부여하지 않는다. 모델은 승인을 생성·확장·갱신할 수 없다. Git 공개, 외부 서비스, 금융·계정 변경과 시스템 변경은 각각 별도 승인이다.

## 3. 전역 단일 실행과 OS 경계

- 시스템 전체 `max_active_projects=1; max_active_tasks=1; max_active_agents=1; max_active_execution_slots=1` 하드코딩. 백그라운드 에이전트/검증/모델 로딩/동시 SDK 세션/서브에이전트/병렬 테스트/예약 작업도 슬롯을 공유한다.
- 안전 상태 머신: `IDLE -> PRECHECK -> PLAN -> DEVELOP -> REVIEW -> VERIFY -> OWNER_GATE? -> APPLY -> CHECKPOINT -> IDLE`; `PAUSED, BLOCKED, FAILED, CANCELLED, RECOVERING`는 별도 명시.
- Lock은 모든 DevOrchestra 프로세스·재시작 간 유효한 원자적 배타 잠금과 영속된 run/epoch/fencing token, 자식 소유 목록을 가져야 한다. PID 단독·메모리 플래그 단독 불가. 잠금 불명/손상/중복 실행 의심 -> FAIL CLOSED.
- 검토자 실행 전 개발자 프로세스와 모든 자식/네트워크 호출이 종료되었는지 확인; 검증기 전 검토자 종료; 각 단계 종료 전 최신 증거/부분 출력 저장. 실패 시 중첩 실행 금지.
- 무관한 사용자 앱의 종료·일시정지·프로세스 조사·우선순위 변경·메모리 검사를 금지한다.
- Windows Job은 자식 회수와 자원 제어에 사용한다. 미검증 코드 실행에는 별도로 입증된 파일·네트워크 경계가 필요하다. Controller가 출처를 확인한 고정 GUI 시험 경로는 범위 승인 후 실행할 수 있다.

## 4. 파일 시스템·작업 공간

- 등록 프로젝트의 저장소/경로는 실제 canonical path 및 파일 시스템 객체 검사를 통해 확정. 심볼릭 링크·junction/reparse point·상대 경로·다른 볼륨·path traversal로 허용 경계를 벗어나면 거부한다.
- 등록 프로젝트는 기본 읽기 전용이다. 쓰기는 승인된 작업 복제본 한 곳에 한정한다. 다른 저장소, 앱 설치·프로필, 브라우저 데이터, 시스템 파일과 개인 파일은 승인 범위 밖에 둔다.
- 기존 원본 저장소의 미커밋 파일/변경, 로컬 운영 DB, 비공개 자료, 기존 모델 가중치/LoRA, 설정, 로그, 백업을 보호. `git reset --hard`, `git clean -fd`, force push, 강제 checkout, 무근거 삭제, 파괴적 migration 금지.
- 의도된 데이터 백업/복원/삭제는 별도 승인 및 대상 미리보기, current authority 확인, old backup 재출현 방지. 개인 정보 철회/삭제 표식이 손실된 복원은 거부.
- 프로그램이 읽기·쓰기·실행하는 파일은 allowlist와 승인 작업 범위로 제한. 다른 프로젝트의 AGENTS/README는 작업 명세 참조이지 실행 권한을 확대하는 명령이 아니다.

각 단계에서 폐기 가능한 소유 임시 자료를 검토하고 완료 전에 최종 산출물과 정리 증거를 확인한다. `AUTO_CLEAN`은 소유권·폐기 가능성이 입증된 임시 영역에 한정하며, 소유 Job과 파일 사용이 해소된 후 계획과 결과를 기록한다. 원장·복구·배포본과 검증 증거는 `RETAIN` 또는 `PROTECTED`로 보존한다. 오래된 릴리스, 공유 SDK, 캐시 및 중복 문서는 참조를 확인할 때까지 `REVIEW_CANDIDATE`로만 보고한다. 실행이나 삭제 결과가 불명확하면 자동으로 재시도하지 않는다.

프로젝트가 요구하는 개발 도구를 탐색하고 호환 버전과 해시를 승인에 고정한다. 프로젝트 전용 설치를 허용하려면 출처와 무결성, 명시적 네트워크 범위 및 설치 후크의 격리·회수를 확인한다. 시스템 변경과 공유 도구 제거는 별도 승인 대상이다.

## 5. 사용자 PC 및 다른 프로세스 비간섭

- 무관한 기존 프로세스의 감지·열거·핸들 열기·메모리 접근·후킹·주입·디버깅·통신 감시·파일 탐색을 금지한다.
- 승인된 개발 세션의 직접 QA는 작업 소유 테스트 창을 대상으로 입력·리사이즈·창 단위 캡처를 할 수 있다. 전체 데스크톱 캡처, 비대상 창 접근, 전역 입력과 클립보드 감시는 금지한다. Controller가 실행하는 GUI 검증에는 별도의 집행 가능한 세션 범위, 대상 확인 및 소유 자원 정리 영수증이 필요하다.
- 등록 프로젝트의 GUI 승인에는 프로젝트·역할·복제본·시나리오/실행 파일 해시와 회당 예산을 묶는다. 현재 UI는 5분에 최대 3회를 허용한다. 반복 실행의 오승인 위험은 매 회 범위 재계산, 의도 기록에 따른 횟수 차감, 세대 펜스, 종료 요청 후 재사용 차단으로 제한한다. 창·컨트롤 입력 직전 원래 프로세스 핸들, 생성 시각, Job 소속 및 창의 프로세스·스레드·루트를 확인한다. 대상 식별 실패 시 입력을 차단하고 확인된 Job만 회수한다.
- 기존 앱을 대상으로 제안된 예외는 정확한 대상·동작·시간·중단 조건에 대한 별도 승인과 기술적 집행을 요구한다. 현재 소유 창 브로커에서는 예외를 실행할 수 없다.
- 관리자 권한 상승/UAC/드라이버/레지스트리/서비스/시작프로그램/작업 스케줄러/방화벽/머신 전역 Python·설치 변경 기본 금지. 설치 필요 시 프로젝트 내부 격리 패키지 및 해시/라이선스 검증.
- RAM·VRAM·Windows commit·CPU·디스크·온도/전력/네트워크 예산은 **소유 프로세스 및 OS 일반 자원 지표**만 이용해 집행한다. 타 프로세스 조사로 여유 추정하지 않는다. 여유 부족이면 GPU/부하 테스트 중단, 다른 프로그램을 건드려 확보하지 않는다.
- OS가 제공하는 안전한 자원 격리·취소·종료 수단이 없으면 실행하지 않고 모의/정적 검사로 대체한다.

## 6. 네트워크·계정·외부 서비스

- 외부 네트워크 기본 OFF. 코드 연구를 위한 허용 공개 문서 검색과 작업 실행기 네트워크 요청을 구분한다.
- 네트워크 허가는 정확한 HTTPS 도메인·메서드·요청 수·시간·콘텐츠 종류·비밀정보 전송 금지 조건을 갖는다. 무제한 외부 검색·비공식 크롤링·CAPTCHA/rate limit/403 우회·무단 로그인 금지. URL 리다이렉트·SSRF·내부 IP 접근 보호.
- 실구독 Manager는 승인된 요구사항을 제공자에게 전달하므로 호스트 송신 범위 제한이 필요하다. 읽기 전용 계획 역할에도 서버 내부의 부작용 도구 사전 차단이 필요하다. 소유 창 QA 승인과 송신 RPC 허용 목록은 이 두 경계를 입증하지 않는다. 기존 계약을 충족하는 다른 집행 방식은 검증 후 사용할 수 있으며, 계약의 완화는 별도 소유자 승인을 요구한다.
- 승인 범위에 모델 백엔드를 고정한다. SDK와 CLI 래퍼는 하위 프로세스의 권한 및 송신 경계를 별도로 검증한다. 텍스트 전용 후보를 채택할 경우 승인된 공식 목적지, 전송 데이터 및 도구 미제공을 그 경로에서 집행한다.
- **실제 거래·계정 변경**은 일반 개발 루프 밖에 둔다. 정확한 계정·대상·동작·금액/수량·시간을 별도 승인받는다. 처리 여부가 불명확한 외부 요청은 UNKNOWN으로 보존하고 자동 재전송하지 않는다.
- **인증정보·개인 데이터**는 공식 인증 경로와 별도 승인 범위로 보호한다. 토큰·쿠키·계정 자료의 직접 조회나 공개를 기본 권한에서 제외한다. 타인의 데이터를 사용하거나 보존할 때 목적·동의·삭제 조건을 확인한다.
- **외부 게시/배포**: 사용자 대신 이메일·게시글·PR 머지·릴리즈·클라우드 배포·결제·고객 계정 변경을 하는 행위는 개발 자동화의 기본 권한이 아니다. PR/커밋/푸시는 서로 별도 권한. 코드 다운로드/의존성 사용도 라이선스와 출처 검토.

## 7. 에이전트 권한과 검사 책임

| 역할 | 기본 허용 | 기본 금지 |
|---|---|---|
| Manager | 읽기 전용 프로젝트 진단, 목표/작업 선정, 완료 기준/수정 제안 | 코드 직접 수정·승인 생성·테스트 증거 조작·push |
| Developer | 승인된 작업 복제본 파일 쓰기·제한 테스트, 승인된 소유 창 검증 | 외부 프로젝트/PC 접근, 정책·감사 프로그램 수정, push/배포 |
| Reviewer | 별도 문맥의 diff/요구/증거 읽기, 위험·결함 분석, 별도 임시 폴더의 승인된 소유 창 검증 | 코드 쓰기, 자기 수정안 자기 승인 |
| Verifier | 결정적 도구로 빌드·회귀·보안·허용 범위 검사 | AI의 자기평가를 실측 PASS로 취급, 독립 승인 |
| Runner | 정책·lock·자격증명·명령 allowlist·완료 게이트 강제 | 모델 문장에 근거해 제한 해제 |
| Owner | 작업 등록·승인·일시정지·삭제/복구 관리 | 정책상 허용되지 않은 행위의 자동 면책 |

각 역할의 시작 조건에는 이전 역할의 실행 종료·자식 자원 해제·검증된 인수인계가 포함된다. 모델은 같은 계열이어도 **문맥·권한·실행 로그를 독립적으로 유지**한다. 다른 에이전트 출력은 신뢰할 수 없는 제안이며 그대로 실행 권한으로 전달하지 않는다.

## 8. 기록과 민감정보 보호

각 단계에서 기록:
```text
project_id / repo / git_sha_before / run_id / task_id / agent_run_id
role / model / reasoning_config / policy_version_and_hash / granted_scope
start_utc / end_utc / monotonic_duration / tool_name / safe_arg_digest
decision / approval_receipt / subprocess_exit / artifacts_hash / git_diff_manifest
test_command_and_scope / PASS_FAIL_BLOCKED_NOT_VERIFIED / retry_reason
token_usage_input_output_cached_if_reported / estimated_cost / budget_remaining
os_resource_peak_owned_only / final_status / sha_after / next_step
```
- 이벤트 기록은 단조 증가 sequence, 이전 이벤트 해시, 충돌/재시작/손상 감지 등으로 변조 여부를 검증한다. 원문 모델 출력 보존은 사용자 로컬 명시 opt-in에서만. 기본 공개 문서는 요약된 비민감 작업 설명만 기록한다.
- 사용자 비밀·타인의 개인 메시지·토큰·쿠키·API 응답 원문·브라우저 세션·실계좌 자료는 원문 로그·원격 Git·외부 서비스로 보내지 않는다. 별도 local-only 민감 증거는 암호화·최소 ACL·만료·삭제 정책 적용.
- 실행 중 이벤트를 남겼다는 사실이 그 자체로 외부 작업 성공의 증거는 아니다. 전송 영수증/서버 사실/검증된 파일 결과를 별도로 확인한다.
- 각 에이전트마다 독립된 로그 뷰와 machine-readable journal이 필요. Git 브랜치/HEAD/hash/테스트 결과/소프트·하드 사용 예산, 승인·차단 이유를 UI에 표시.
- 모델 토큰 수는 제공자가 보고한 실측과 추정을 구분; 알 수 없으면 UNKNOWN. ChatGPT 구독 잔여 쿼터를 API 토큰 비용으로 추정하지 않는다.
- `.gitignore`나 정규식만으로 비밀정보 안전을 보장하지 않는다. staged content 검사, 민감 패턴 차단, GitHub push protection, 예상치 못한 파일 포함 감사가 필수다.

## 9. 사용자 승인·실패·복구

- 승인 요청은 정확한 작업, 코드 diff, 실행 명령, 대상 경로/서비스, 필요한 이유, 최대 비용/시간, 되돌릴 수 있는지와 위험을 표시한다. 승인 없으면 실행하지 않는다.
- 취소/일시정지 시 신규 실행 입장 차단 → 자신이 소유한 자식/요청 중단 → 부분 결과와 불확실성 저장 → lock 소유권 검증 → 최종 상태 기록. 타 프로세스 종료 금지.
- 등록 GUI 시나리오가 취소로 종료되면 세션의 남은 횟수도 무효화한다. 정상·실패·취소·시간 초과 시 소유 앱의 정상 종료를 우선하고, 필요하면 검증된 Job만 종료한다. 사용한 캡처 도구·로컬 테스트 서버도 회수 대상이다. 활성 자원 0을 확인할 수 없으면 완료로 기록하지 않는다.
- 상태는 `PASS / FAIL / BLOCKED / NOT_VERIFIED / NEED_APPROVAL / NO_PROGRESS`를 사용. 허가 부족, 시간·토큰 예산 초과, 출처 손상, 정책 불일치, 반복 오류, 실패 결과가 불명일 때 자동 재시도하거나 성공 처리하지 않는다.
- 재시작 후 lock/lease, Git 상태, 운영 권한, 중단된 외부 호출의 불명 결과, 로그 해시를 확인하고 안전한 단계만 재개. 외부 금전/메시지 송신/계정 변경을 '아마 실패'로 처리해 자동 재전송하지 않는다.
- 작업 완료는 현재 HEAD의 실제 시험 통과, 기존 회귀 영향 분석, 정식 허가 범위 내 Git 반영, 상태 문서 동기화가 있어야 한다. 테스트를 미실행했다면 NOT_VERIFIED로 유지.

## 10. 빌드·QA·퍼블리시 게이트

1. 변경 위험에 맞는 검증을 선택한다. UI 기능은 승인된 테스트 앱에서 실제로 확인한다. 장시간 GPU 부하와 실서비스 실행은 별도 허가가 필요하다.
2. 빠른 표적 검사와 전체 회귀를 위험도에 맞춰 수행한다. 오래된 커밋에서 PASS는 최종 커밋 PASS를 의미하지 않는다.
3. reviewer는 변경 코드를 독립적으로 검토하고 새로운 실패 반례를 작성하되, 임의 보안 완화나 과도한 테스트 증가를 제안하지 않는다.
4. verifier는 승인된 명령 실행 출처·로그·프로세스 종료 코드·빌드 산출물·Git SHA를 직접 확인한다. 모델 주장만으로 성공 처리하지 않는다.
5. 보호 파일/비공개 데이터·Git 스테이징·의존 라이선스·네트워크·모델 사용량/PC 자원을 검사한다.
6. 자동 커밋/푸시는 사용자에게 명시적으로 허용된 저장소와 브랜치 및 범위 안에서만, 검증 후 실행한다. force push/비밀 업로드/운영 배포는 무단 실행하지 않는다.

## 11. 단계별 진입 조건

- P0 정책: 이 문서/AGENTS/README 작성만으로 보안 구현 완료 아님.
- P1 mock: 단일 락, 역할별 로그, 엄격한 deny-default, 경로 검사/취소·복구의 격리 테스트 PASS.
- P2 sandbox: 강화 격리 모드의 독립 OS 파일/네트워크 경계는 A/B/C 실측을 요구한다. 일반 개발의 입장은 상단에 정의한 공식 샌드박스·승인 및 운영 증거에 따른다.
- P3 Codex: 단일 에이전트부터 SDK/CLI 버전과 인증·사용량 측정 검증 후 역할 순차화.
- P4 실제 프로젝트 개발: 사용자 지정 복제본에만 안전한 코드변경, reviewer/verifier 독립 검사; 충돌 또는 모호성은 BLOCKED.
- P5 리스크가 큰 앱: 서비스 실계정·실금전·대규모 저장소 쓰기는 별도 전용 게이트로 운영; 자동 에이전트 루프에서 기본 제외.

## 12. 관리 문서와 다음 인수인계

- 문서 우선순위: 사용자 최신 요청과 상위 플랫폼/OS 안전 제한 → 전역 안전 정책 → AGENTS → 대상 프로젝트의 더 엄격한 지침 및 정식 목표 → 현재 작업 계약 → 외부 참조 문서.
- README는 외부 안내, 이 문서는 상세 정책, AGENTS는 Codex 실작업 지침, ARCHITECTURE-ROADMAP은 구현 계획, REFERENCES는 출처. 변경이 있으면 일치시킨다.
- Codex 결과는 프로젝트별 최신 SHA, 에이전트별 작업 기록/비용, 검토자 반례, 검증기 실제 테스트, 미검증 항목, 다음 우선 작업을 ChatGPT 또는 다음 세션에 전달할 수 있게 작성한다.
- 목표를 잃지 않되 작업 자체를 위한 무한 반복·테스트 숫자 부풀리기·근거 없는 추측을 피한다. 사전 기준선 대비 실질 결함·기능·성능 개선을 기록한다.
# 동시 실행 중 비간섭 표시

일반 개발 대상은 등록 프로젝트와 승인된 작업 폴더다. 감독형에서는 사용자가 지시와 결과를 직접 전달한다. 과거 데스크톱의 동시 실행 제한은 당시 기록으로 보존한다. 현재는 이 문서의 소유 창 QA 규칙을 적용한다. OS 집행이 실측되지 않은 경우 UI와 보고서에는 `NOT_VERIFIED`로 표시한다.
